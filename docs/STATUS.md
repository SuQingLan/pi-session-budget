## 一、这是什么

pi / pi-web 的常驻状态行扩展：在输入框上方实时显示当前会话花了多少钱、用了多少 token、
缓存命中率、上下文占了多少，并把**子代理（subagent）**的用量一并计入。

与同类工具（跨会话账本 + 浏览器仪表盘那一类）相比，本项目的取向是：

| 取向 | 本项目 | 另一类（账本 + 仪表盘） |
|---|---|---|
| 时间维度 | **实时**（事件驱动 + 周期自愈） | 事后统计（30 秒增量扫描） |
| 币种口径 | **人民币原生**（中转站时段/阶梯价） | 美元账本 × 汇率 |
| 子代理 | **递归统计**（多层嵌套） | 通常不覆盖父子链 |
| 交付形态 | 单文件扩展，clone 即用 | npm 包 + 前端页面 |

## 二、当前能力

- **费用累计**：按每次调用的 usage 计价，支持预算与超预算告警（`/budget`）
- **缓存命中率**：`缓存读 / (输入 + 缓存读 + 缓存写)`，主会话与子代理分列
- **子代理递归统计**：沿 `parentSession` 做 BFS，含子代理再派子代理
- **跨会话去重**：sha1 指纹，fork/clone 副本不重复计费
- **真实 / 估算成本分列**：单独统计，`/budget` 输出构成行
- **上下文占用**：读 `settings.json` 的 `reserveTokens`，与 pi 实际压缩时机一致
- **按 profile 拆分**：子代理行末尾给 worker / reviewer / scout 等小计
- **历史重算**：每次渲染按**当前**价格表重算全部历史调用
- **费用回写**：把算好的费用写回消息，pi-web 自带的费用显示随之准确
- **脱敏**：仓库不含站点地址、账号、密钥、价格表、会话文件

## 四、已知问题与限制（重点）

### A. 金额口径

**A1. 装了价格表之后，真实成本不计入总额** —— 最容易让人误判的一条

计价优先级是 `价格表 > models.json > usage.cost.total`。价格表命中时，整条调用按**估算**计价，
而 pi 记录在消息里的 `usage.cost.total`（**真实花费**）被跳过。

- 现象：widget 显示的 ¥ 是估算值，与服务商账单可能有差；`/budget` 的构成行会显示「真实成本未记录」
- 影响：金额的**绝对值**可能不准（估算 vs 真实）；相对比例、趋势、预算百分比不受影响
- 现状：这是为了保证人民币口径一致而有意做的取舍，不是 bug
- 可选改进：加一个开关，同时显示真实美元成本；或让真实成本单独一行

**A2. 工具内部的嵌套 LLM 调用不计入**

本项目只统计 `role === "assistant"` 的 usage。`toolResult` 消息里若嵌有 LLM 调用（工具自己调模型），
这部分开销不计入（另一类工具会计入）。

- 影响：某些扩展/工具密集的场景，总额会偏低
- 可选改进：按需计入 `toolResult` 的 usage

**A3. 费用显示最多滞后 1 秒**

子代理扫描有 1 秒节流缓存，防止高频事件反复扫盘。代价是新产生的子代理用量最多滞后 1 秒才出现。

**A4. 压缩本身有成本，但不重复计**

`compaction` / `branch_summary` 只计顶层 usage，`retainedTail` 里是历史消息副本（不重复计）。
这条是正确的，但要知道：**压缩调用也会花钱**。

### B. 去重与归属

**B1. fork 出去的新分支，花的钱会计到原会话头上** —— 已知缺陷，未修

会话被 fork 时，新会话文件同样带 `parentSession`，于是被 BFS 当成"后代"。
- 历史部分：靠指纹去重，不会重复计 ✓
- **fork 之后新产生的调用**：会算进原会话的子代理账上 ✗

- 影响：fork 场景下归属错误（金额会偏高，且记在错的会话上）
- 根因：子代理会话文件第 1 行有 `pi-web:subagent` 标记，fork 副本没有 —— 可据此区分
- 可选改进：把没有该标记的后代单独归为 `fork` profile，或直接排除并单列提示

**B2. 极低概率的误去重**

指纹为 `sha1(entryId | ts | provider | model | 四项 token)`。摘要类记录已统一为"带 entry id + 空 provider/model"，
残余风险仅限于：两个不同会话在同一毫秒产生完全相同的 usage 且都没有 entry id。

### C. widget 刷新

**C1. 周期重绘的开销随窗口数线性叠加**

- 实测：单次渲染约 **11.5 ms**（主要是 stat 一遍 `sessions/` 下的会话文件），默认每 2 秒一次
- 折算约 **0.6% 单核 / 会话**；开 10 个窗口约 6%
- 缓解：`refreshMs` 调大或设为 `0` 关闭（关闭后就回到"错过推送就一直空着"的旧行为）

**C2. 连击输入时状态行最多滞后 400 ms**

`input` 事件单独做了 400 ms 节流（其余事件立即渲染）。

**C3. pi-web 前端的 widget 展开状态存在前端本地 state，重挂载不保留**

若页面上有多个 widget，重挂载后展开的可能不是本项目这一块。**扩展侧无法解决**，
只能表现为"有框但看不到内容"（与"整块空白"可区分）。

**C4. 会话被空闲回收时可能留下一个孤儿定时器**

定时器带 `unref()`，不阻止 pi 进程退出；宿主派发 `session_shutdown` 时会正常停止。
极端情况下（宿主未派发 shutdown）会残留一个 unref 定时器，资源占用可忽略。

### D. 工程与协作

**D1. 契约测试用 mock 宿主，发现不了上游签名变更**

mock 是手写替身，不会随上游 pi 变化。上游把 `ui.setWidget` 改名 → 符号存在性检查能挡住；
上游把 `setWidget` 的**参数**改了 → 挡不住。

**D2. 没有类型层检查（`tsc`）**

项目坚持「运行时零依赖、clone 即可跑」，未引入 `typescript` + 宿主包作 devDependencies。
代价就是 D1 里的签名变更挡不住。

**D3. 没有 CI**

所有测试靠本地手动跑（`npm test` / `npm run check:host`）。提交前请自己跑一遍。

**D4. 推送需要代理**

本机 `git config --global http.proxy` 未设置，直连 github.com:443 会超时。
若推送失败：`git -c http.proxy=http://127.0.0.1:7897 push origin main`，
或把代理写进全局配置。

### E. 上游兼容

**E1. `session_info_changed` 的作用有限**

该事件的语义是「会话名称元数据变化」（`{type, name}`），**切会话时并不触发**。
监听它基本没用（保留无害）。

**E2. 宿主没有"UI 重新附着"类事件**

已查遍宿主的 `dist/`、`docs/`、`CHANGELOG.md`：`focus` / `visibility` / `attach` / `resume` /
`onSessionRestore` 之类的扩展事件与回调**均不存在**。
这是为什么必须靠**周期性重推**来自愈，而不是等一个"重新附着"钩子。

### F. 隐私与安全

**F1. 历史里留有一个提交包含 `.pyc`**

`57dfe46` 已从仓库移除该文件并补了忽略规则，但 **git 历史中仍可检出**。
`.pyc` 不含凭据，风险很低；若介意可用 `git filter-repo` 重写历史（会改写所有 commit id）。

**F2. 仓库不含敏感信息**

站点地址不在源码里（由 `CM_BASE` 指定，或从已有价格表的 `source` 字段回填）；
口令只走环境变量；站点 API Key 只做前缀匹配，不写进生成的价格表。

cd <仓库目录>

1. `💰` 行的金额前缀 —— 全为估算时应带 `≈`

3. `/budget` 的构成行 —— 应与 widget 总额一致

## 附：与 `pi-monitor` 一类项目的差异

调研过 `Nana7mi-swjtu/pi-monitor`（跨会话账本 + 本地仪表盘，18k+ 行，含 26 份测试夹具与 quality-gate）。
本项目在它的基础上补了它没有的东西，也从它身上学了几件事：

**本项目领先**：子代理递归统计（它没有父子链概念）、人民币原生计价（它只能美元×汇率）、
实时状态行（它明确不做「本会话实时卡」，因为内存计数在多进程下会失效 —— 本项目用"每次读盘 + mtime 缓存"绕开）。

**本项目欠缺的**：账本化与增量游标（它有 `ledger.jsonl` + `cursor.json`）、
真实成本与估算的严格分离（它是 `MoneyTotals{known, estimated}` 两个字段）、
模块化拆分（它 26 个 `src/` 模块 + 纯函数分层，本项目单文件）、
测试体系规模（它 unit/integration/contract/golden/fixtures/bench 六层，本项目 63 个用例集中在 unit+contract）、
CI 与 quality-gate。

值得后续借鉴的：**增量游标**（会话文件极多时本项目每次渲染都要 stat 一遍）、
**模块化拆分**（本项目扩展已近 900 行）。
